## 1. P1：优先修复的正确性问题

### B01 连续重命名丢失最终路径，Stage All 会漏提交

- 触发：已有文件 A，先暂存 A→B，再在工作区将 B→C，点击 Stage all，然后 Commit。
- 实测：客户端只返回 path=B、original=A、index=R、worktree=R，没有 C；Stage all 报成功，提交树却为空，C 留在磁盘上成为未跟踪文件。不是正文已被物理删除，而是用户以为完成的提交遗漏正文。
- 根因：状态模型优先采用 HEAD→index 的 rename，丢弃 index→worktree 的新路径；批量暂存随后按已不存在的 B 处理。
- 位置：[libgit.rs:149](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:149)、[libgit.rs:831](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:831)。
- 建议：分别表示 HEAD、index、worktree 的路径；按各层变化生成暂存操作，不能用一组 original/path 同时代表两层 rename。
- 证据：target/core_audit.rs；target/core_audit_results.txt；隔离仓库 target/core_audit_repos_v2/rename。

### B02 重命名后复用旧文件名，Stage All 又撤掉新文件

- 触发：暂存 A→B，再创建一个新 A，点击 Stage all。
- 实测：先暂存新 A，随后处理 B 时 remove_path(original A)，把刚暂存的 A 再次移除。提交仅含 B，A 仍未跟踪，提示仍为 All changes staged。
- 位置：[libgit.rs:832](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:832)。
- 建议：统一规划删除与新增的顺序，优先处理旧索引项，再处理实际工作区目标；补充 rename-source reuse 回归。此问题和 B01 的修复点不同，应分别测试。
- 证据：target/core_stage_audit.rs；target/core_audit_results.txt。

### B03 远程分支与本地分支同名时，Merge 选错目标

- 触发：同时存在 refs/remotes/origin/main 与 refs/heads/origin/main，在远程分支菜单选择 Merge。
- 实测：界面传入不带命名空间的 origin/main；后端优先查本地分支，HEAD 变成错误的本地提交，实际树含 LOCAL 而不含远程目标的 REMOTE。
- 位置：[modals.rs:267](/Users/liming/Code/Github/MyCode/gitbuddy/src/ui/modals.rs:267)、[libgit.rs:909](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:909)。
- 建议：操作携带完整 refs/heads 或 refs/remotes 名称及确认时的目标 OID，禁止通过本地优先的字符串猜测选定对象。
- 证据：target/core_audit.rs；target/core_audit_repos_v2/ambiguous_merge。

### B04 普通 Commit 会破坏外部 Git 发起的 Rebase

- 触发：外部 git rebase 有两步，第一步冲突；解决并暂存后，在 GitBuddy 使用普通 Commit。
- 实测：Commit 成功后删除 rebase-merge；第二步没有重放，原 feature 分支未更新，HEAD 仍 detached，git rebase --continue 报 no rebase in progress。主任务重新运行了同一复现并确认。
- 根因：UI 仅检查 staged 数和索引冲突；后端仅阻止 GitBuddy 自有 Rebase，普通 commit_index 对任何非 Clean 状态都 cleanup_state。
- 位置：[detail.rs:121](/Users/liming/Code/Github/MyCode/gitbuddy/src/ui/detail.rs:121)、[ui.rs:843](/Users/liming/Code/Github/MyCode/gitbuddy/src/ui.rs:843)、[libgit.rs:869](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:869)、[libgit.rs:1200](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:1200)。
- 建议：UI 和 API 共用操作资格检查；未支持的外部流程只能查看/解决，不允许普通提交清理其状态。状态清理只由明确的 Continue/Abort 流程负责。
- 证据：target/ui-audit-native-rebase.py、target/ui-audit-api.rs。

### B05 GitBuddy Rebase 在崩溃恢复窗口中静默漏掉补丁

- 触发：pending=true 已保存，libgit2 已写 CHERRY_PICK_HEAD，但尚未完成 checkout/index 写入时进程终止，再 Continue。
- 实测：构造这一持久化中间状态后，Continue 报 Rebase complete，新提交保留 feature 说明，但 required 文件不在提交树或工作区；状态被清理。原提交仍在备份引用，可人工恢复。
- 根因：恢复仅校验 marker、无索引冲突及无未暂存变化，将旧 onto index 当作已应用结果。当前 vendored libgit2 cherrypick.c 第 202 行先写 marker，第 208–209 行才 checkout / 写 index，所以该中间状态对应真实终止窗口，不是任意篡改状态。
- 位置：[rebase.rs:437](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/rebase.rs:437)、[rebase.rs:448](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/rebase.rs:448)。
- 建议：区分 applying、applied、resolving、commit-prepared 阶段；检查索引写入状态/残留锁，不能把 marker 存在视为补丁已经应用；增加 marker 已写而 index 未写的恢复测试。
- 证据：target/advanced_audit_rebase.rs。属于运行 API 的崩溃状态模拟，未进行随机 kill 或断电实验。

### B06 LFS 冲突解决直接提交正文，绕过指针转换

- 触发：LFS 文件 Merge 冲突，修改工作文件后选择 Use working file 或编辑结果，Save & mark resolved，再 Continue。
- 实测：提交 blob 为 resolved binary content 正文，lfs_status_files=0，操作报告成功。后续历史里的该版本不再是 LFS 指针。
- 根因：冲突保存直接 repo.blob(bytes) 写索引，未调用 LFS clean；普通 Merge 已复现，Rebase 复用同一保存 adapter。
- 位置：[conflicts.rs:475](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/conflicts.rs:475)、[conflicts.rs:503](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/conflicts.rs:503)。
- 建议：冲突索引安装也使用统一 LFS clean 入口，缓存和验证对象，再安装指针；不支持的情况明确拒绝。完整版本选择、手工编辑和工作文件选择都要覆盖。
- 证据：target/advanced_audit.rs。

### B07 属性宏绕过 LFS 引号规则拒绝，Stage All 存储正文

- 触发：.gitattributes 定义 [attr]bigfile filter=lfs diff=lfs merge=lfs -text，再使用带引号的规则 "my file.bin" bigfile。
- 实测：系统 Git check-attr 返回 filter:lfs，客户端 Stage all 报成功，索引却存入 content intended for LFS 正文。
- 根因：拒绝逻辑只识别引号行直接含 filter=lfs，未识别宏。libgit2 不识别引号模式时返回不匹配，后端退回普通 index.add_path。
- 位置：[lfs.rs:141](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/lfs.rs:141)、[lfs.rs:136](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/lfs.rs:136)、[lfs.rs:191](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/lfs.rs:191)。
- 建议：对不支持的属性语义可靠拒绝，覆盖宏展开/继承规则，避免将未知属性解释为普通文件。
- 证据：target/advanced_audit_attributes.rs。当前 README 声明引号规则不支持，但本例绕过了预期的安全拒绝，因此属于 Bug。

### B08 Worktree 删除会丢失被 ignore=all 隐藏的子模块编辑

- 触发：关联工作树含已初始化子模块，.gitmodules 配置 submodule.child.ignore=all，子模块 tracked 文件有未提交编辑，再移除工作树。
- 实测：module_dirty=true、worktree_dirty=false；RemoveWorktree 成功，子模块编辑文件被整个目录删除。对照系统 Git worktree remove 拒绝含子模块的工作树。
- 根因：只检查父仓库 clean；status 遵循子模块 ignore 配置，随后 prune(working_tree=true) 删除目录，没有递归检查。
- 位置：[workspaces.rs:161](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/workspaces.rs:161)、[workspaces.rs:168](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/workspaces.rs:168)、[libgit.rs:139](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:139)。
- 建议：删除资格不依赖 UI/status 的忽略策略；递归检查子仓库和未跟踪内容，或先明确拒绝含已初始化子模块的移除。普通 ignored 文件随工作树移除的行为没有被列为 Bug。
- 证据：target/advanced_audit_submodule.rs。

### B09 Stash 使用易变序号，旧确认会删除另一条记录

- 触发：打开 stash@{0} 的删除确认，外部再保存一条 Stash，再确认旧请求。
- 实测：旧记录的 OID 仍在，新记录反而被删除，操作显示 Stash deleted；ApplyStash 也会应用错误记录。
- 根因：Snapshot 丢弃 stash_foreach 返回的稳定 OID，保存 stash@{i}；执行时只解析当前序号，没有核对原目标。
- 位置：[libgit.rs:574](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:574)、[libgit.rs:1064](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:1064)、[libgit.rs:1068](/Users/liming/Code/Github/MyCode/gitbuddy/src/git/libgit.rs:1068)。
- 建议：使用 stash OID 表示选择，执行前重查当前序号且再次校验；变化后拒绝过期确认，而不是对新序号直接操作。
- 证据：target/core_stash_audit.rs；target/core_audit_results.txt。
